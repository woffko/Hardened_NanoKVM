# Hardened NanoKVM 2.1.0 RC13 + System 0.4.0 Raw 1

This release fixes what a full security audit of RC12 found, and moves the kernel
to Linux 5.10.272. It keeps the production signing key
`hardened-system-prod-2026q3` and RSA/SHA-256 signatures.

## Required install order

Keep a recovery SD card at hand and the power connected. A raw update rewrites
the boot and root partitions and takes about 15 minutes.

1. **Application first.** Install `2.1.0` before the system update: through
   **Settings → Update** with **Preview Updates** on, or through **Offline
   Update**. The system update refuses to install under an older application.
2. **System `0.4.0-raw.1` next.** In the **System Update** section press
   **Refresh**, enable **Allow raw system updates**, select **Download and
   Verify**, then install the staged update. The device reboots by itself and
   restores its settings on the first boot. Disable **Allow raw system updates**
   again afterwards.
3. **The full SD image** already contains both and needs neither step.

An installation older than application `2.0.42` first takes the `2.0.42` trust
bridge, as described in the
[key-transition notes](https://github.com/woffko/Hardened_NanoKVM/blob/hardened-system-0.4.0-raw.1/docs/releases/2.0.42-key-transition.md). A system older than
`0.3.0-raw.12` first takes `0.3.0-raw.12`: this release names it as the oldest
system it can restore from, and refuses older ones before anything is
downloaded.

## What changes for you

- **Offline Update needs the signature.** From `2.1.0` on it takes the archive
  together with `latest.json` and `latest.json.sig` from the release. A session
  alone no longer installs code as root. Application `2.0.42` still takes the
  archive by itself, so the step to `2.1.0` works as before.
- **First setup needs a claim token** on a new card. The device prints a
  one-time token on the serial console and keeps it in
  `/etc/kvm/first-boot-claim` for root. It is never written to a log.
- **A new card starts on HTTPS** with a generated certificate. A device that
  uses HTTP stays on HTTP, and an update never switches it.
- **The USB network no longer reaches management.** New connections from
  `usb0` are refused in every firewall mode, ahead of any other rule. Creating
  `/etc/kvm/usb_management` and restarting the firewall opens it.
- **BusyBox is no longer setuid**, so `su` works only from root.
- **An unusable SSH host key is replaced.** OpenSSH 10.6 cannot read the MLDSA
  host key that earlier systems generated. The device replaces that one key by
  itself on a reboot and goes on offering an MLDSA host key. The classical keys
  that clients pin do not change.
- **Uploaded scripts survive a raw update without their execute bit.** They run
  when you ask, and they do nothing by themselves.

## Raw updates

- A raw attempt that never reaches the writer can no longer lock a device out.
  The running system stops needing the boot ticket before an attempt is
  published, and a restored system stops reading it after its first boot.
- Nothing is written until both partitions have opened and proved large enough
  and both images have been hashed again after the system stopped.
- The first 4 KiB of the root partition go in last, so an interrupted write
  leaves a root the kernel will not mount. A failure on either partition leaves
  it that way: the device then needs a reflash, and never runs unknown bytes.
- Each partition is read back and hashed after its cache is dropped, and the
  writer's journal says how.
- One image serves every deployed account layout. Service accounts come from
  the image; root and the accounts of people come from the device. A clash with
  one of them refuses the update before anything is written.
- Every OpenSSH 10.6 file in `/etc/ssh` is carried, and a file outside the known
  set stops the update by name.
- The hostname, the saved time zone and the update progress are finished after
  the restore. The image now holds the full time zone database, and a zone it
  lacks falls back to UTC.
- The raw switch is read from disk under the writer drain, so turning it off
  applies to the next attempt. A raw image always needs a release signature.
- A refused application update stops before anything is stopped or drained.

## Application 2.1.0

- Password checks run off the request runtime; the login lockout covers the AP
  key; sessions are pruned and capped at 32.
- Changing a password needs the current one. The root and web passwords change
  through one journal, so the two never diverge.
- The terminal ends its whole PTY session when its login ends. The Picoclaw
  gateway chat closes with the session that opened it.
- Online updates are forward-only and authenticated again before the download
  and before the install. The update page waits for the backend to come back,
  and a failed install stays on screen with its message.
- Firewall changes are one atomic commit per address family, kept as a durable
  pending record and rolled back at the next start if never confirmed.
- Scripts run under a supervisor that ends what they leave behind, with their
  own error when it cannot. Uploads and runs need a fresh terminal unlock.
- Picoclaw keeps operating the connected computer without a per-key approval.
  Its local tool policy is enforced in code, its install and start are
  broker-owned jobs with receipts, and a profile you selected stays selected.
- HID reconnects with a bounded backoff; IME composition types once; a paste
  with characters the layout cannot type is refused by name. One H.264 source
  serves Direct and WebRTC viewers. The EDID tool backs up before any erase.

## System 0.4.0-raw.1

- Linux `5.10.272-tag-`, the signed stable release merged onto the SG2002 vendor
  branch, with the accepted RC12 hardening fragment and `CONFIG_PROC_CHILDREN`.
- Buildroot 2026.05.1 with OpenSSL 3.6.5, OpenSSH 10.6p1, expat 2.9.0, curl
  8.23.0, wpa_supplicant 2.12 and BusyBox 1.38.0 with board patches.

## Validation status

- Two independent application builds and two independent full system pipelines
  from build commit `8837d86` are byte-identical: application archive
  `e03a61f4bd059a4527a8924adc9e6eba7a423154d5af577092747080f4502087`, kernel
  image bundle `df4807a645d9e89410239826f4ad4b982e0fcc572fbbb0fa7b537d3ab3ee0af4`,
  full SD image `75d1e949257dbcc7a992e864fc43ec492e9894b44b316fdf00966b88ca07a129`.
- Host checks on that commit: 1561 Rust tests pass and none fail, Clippy adds
  nothing to its baseline, the host suite has 61 passes, no failures and 9 device
  tests it cannot run. `pnpm audit --prod` is clean. `cargo audit` reports
  `crypto-bigint` through webrtc-rs and warns about `unsafe-libyaml`; both are
  accepted and described in `docs/security-rust-dependencies.md`.
- These exact bytes were installed on two test devices, from the debug build
  before them: the signed application, then the raw update. On both the raw write
  took about 15 minutes and both partitions read back as their images. Settings,
  accounts, the SSH host keys, the TLS pair, the hostname, the network and the
  firewall mode came back, and two more reboots were clean.
- On the device without an HDMI source, an attempt stopped after its ticket was
  published left the device bootable. Uploads without a valid signature and a raw
  install with the switch off were refused. Scripts, the fallback certificate, time
  zones, all four firewall modes and switching TLS off and on again worked. The old
  MLDSA key was replaced by itself and the new one offered.
- On the device with a live HDMI source, MJPEG delivered 1920x1080 frames before and
  after the update, and its saved time zone and NTP server held. That device moved
  from the expanded account layout to the image's numbers on the debug build just
  before this one, which differs from this release only in the SSH key step and the
  version number.

## Not tested in this release candidate

- **The path most devices take: RC12 straight to this release.** The devices above
  came through debug builds. Development builds did update real devices from
  application `2.0.42` and system `0.3.0-raw.12`, but not with this code. A device on
  implicit HTTP is covered by host tests only.
- A full SD image on a clean card, its first boot and the claim token on the
  serial console.
- Power loss during a raw write, a write failing halfway, and the recovery round
  trip from a reflash.
- H.264 and WebRTC streaming and real key presses. MJPEG was tested with a live
  source. Packet-level IPv6 filtering: the rules were checked, not the traffic.
- Picoclaw on hardware: its changes are covered by host tests only.

## Recovery and limitations

- There is no automatic rollback for a raw update. Recovery is a reflash, and
  [`docs/sd-card-flashing.md`](https://github.com/woffko/Hardened_NanoKVM/blob/hardened-system-0.4.0-raw.1/docs/sd-card-flashing.md) describes it. A device
  where a partition write fails needs one.
- The browser cannot tell a changed certificate from an unreachable device. After
  such an update the page asks for a manual reload and names the likely cause.
- The full SD image is the recommended way to evaluate this kernel and system on
  a spare card.
- This release does not claim that the SG2002 vendor delta is free of every
  upstream kernel CVE.
- Vendor firmware and runtime inputs still carry `NOASSERTION` license metadata.
  This is unchanged from RC12 and remains unresolved.
- `serde_yaml` with `unsafe-libyaml` is an accepted, documented residual.
