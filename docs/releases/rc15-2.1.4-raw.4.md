# Hardened NanoKVM 2.1.4 RC15 + System 0.4.0 Raw 4

This release fixes an SSH authentication bypass that affects every earlier
release, and what a second security audit of RC13 found. It keeps Linux
5.10.272, the production signing key `hardened-system-prod-2026q3` and
RSA/SHA-256 signatures. RC14 was never published.

## Security: update if SSH is enabled

**CVE-2026-123158.** OpenSSH before 10.6p2, on a system that uses musl and no
PAM, accepts any password longer than 256 bytes for an account whose stored
password field is `*`, once another account has a password hash. Every earlier
Hardened NanoKVM system matches: its service accounts have that field, root gets
a hash at the first setup, and SSH is on by default.

- **Who can reach it:** any client that reaches port 22 of a device that was set
  up. No password or key is needed.
- **What it gives:** a login as a service account. Those accounts have no shell,
  so there is no command line and no file transfer. Port forwarding works, so
  the device can be used to reach the networks it is attached to, including the
  USB network of the computer it controls.
- **A shell as root** is reachable only on a device where someone changed the
  accounts by hand, for example root with a key and no password next to another
  account that has a password.

What fixes it:

- System `0.4.0-raw.4` carries OpenSSH 10.6p2, and every account of the image
  except root ships locked.
- Application `2.1.4` locks the service accounts of whatever system it runs on,
  as soon as it is installed, without a reboot. Its `sshd` start script refuses
  those accounts by name and turns password login off for any account that has
  no password hash.

Until a device is updated, turn SSH off in **Settings → Device → SSH**, or keep
port 22 reachable only from hosts you trust.

The project attempted the upstream bypass on the RC13 test device with one
300-byte password for the `daemon` account; the attempt was rejected. The
bypass is therefore described from the upstream advisory and code analysis,
not reproduced on that device.

## Required install order

Keep a recovery SD card at hand and the power connected. A raw update rewrites
the boot and root partitions and takes about 15 minutes.

1. **Application first.** Install `2.1.4` before the system update: through
   **Settings → Update**, or through **Offline Update** with the archive,
   `latest.json` and `latest.json.sig` of this release. The system update
   refuses to install under an older application.
2. **System `0.4.0-raw.4` next.** In the **System Update** section press
   **Refresh**, enable **Allow raw system updates**, select **Download and
   Verify**, then install the staged update. The device reboots by itself and
   restores its settings on the first boot. Disable **Allow raw system updates**
   again afterwards.
3. **The full SD image** already contains both and needs neither step.

An installation older than application `2.0.42` first takes the `2.0.42` trust
bridge, as described in the
[key-transition notes](2.0.42-key-transition.md). A system older than
`0.3.0-raw.12` first takes `0.3.0-raw.12`.

## What changes for you

- **Only the release key is trusted.** The key IDs `hardened-system-dev` and
  `hardened-system-test` of the 2026q3 key transition are retired. From `2.1.4`
  on a device refuses update metadata signed with them. The stable system
  channel, which a device with **Preview Updates** off reads, now carries this
  release signed with the release key.
- **Accounts without a password log in by key only.** For root or a person's
  account whose password field holds no hash, `sshd` no longer offers password
  login. An account with a password is unaffected.
- **Nothing runs from `/tmp` or `/dev/shm`.** Both are mounted
  `nosuid,nodev,noexec`. A script still runs through its interpreter
  (`sh /tmp/x.sh`); a program copied there does not.
- **The autostart upload is gone.** Nothing ever ran those files. Files already
  in `/etc/kvm/autostart` stay where they are.
- **Scripts:** an upload or a deletion needs a fresh terminal unlock. At most 64
  scripts are kept, and a hidden name such as `.x.sh` is refused, because a raw
  update could not carry it. A hidden script from an earlier version can still
  be deleted.
- **The serial terminal link asks first.** A link that opens the terminal with
  serial parameters shows the command and waits for a click before sending it.
- **Login:** many wrong attempts from one address now lock that address for
  every user name, not for one name at a time.
- **Reload the page after the update.** The web interface no longer wraps the
  password in a static-key cipher, which protected nothing. A page cached from
  an earlier version cannot log in until it is reloaded. Use HTTPS.

## Application 2.1.4

- Service accounts are locked at every start and after an application update.
- An application update no longer restarts a running `sshd` from the backend
  process scope. A running SSH service keeps running; a stopped service stays
  stopped. A master with the generated wrapper reloads its account barriers on
  SIGHUP; an older master without the wrapper keeps running and receives the
  new barriers at the next boot.
- The login limiter counts failures per source address across all names, bounds
  its memory, and refuses oversized names and passwords before any hashing.
- Wi-Fi: `wpa_supplicant.conf` and `hostapd.conf` are private, and the plain
  passphrase is no longer kept as a comment. The setup access point's flag lives
  where only root can create it, so a local account cannot open the Wi-Fi setup
  routes that need no login.
- Shared directories: the kernel's protections for links, hard links, files and
  FIFOs of other accounts are on, and a PID file counts only if root wrote it.
- Configuration writes take part in the update freeze: SSH, HID, screen, HDMI,
  virtual devices, OLED, web title, host name, Tailscale and preview settings
  are written atomically under the same permit as the rest.
- A raw update names the file it cannot carry instead of failing with a generic
  error, and the temporary file of an interrupted upload no longer blocks it.
- Signature verification refuses every key while the key policy file is missing.
- The update page offers a system release only when it is newer, and shows the
  reason when the device refuses a download or an install.
- Web: the chat renders no images and only absolute HTTPS links; request
  parameters of the system log and Picoclaw session list are sent correctly;
  identifiers come from the browser's random source; the content security
  policy names `base-uri`, `form-action` and a same-origin `connect-src`.
- Native code: bounded parsing of the frame size files and of OLED text, a
  private state file for the hardware monitor, no access point passphrase on
  the serial console, and close-on-exec descriptors.
- `S30eth` validates static network and resolver input from `/boot`; the USB
  gadget takes only a 16-bit hexadecimal vendor or product ID from there.

## System 0.4.0-raw.4

- OpenSSH `10.6p2`. The release tarball was checked against the SHA-256 of the
  release notes and its PGP signature.
- Every account of the image except root is locked. Root stays unset until the
  first setup gives it a password.
- `/tmp` and `/dev/shm` are mounted `nosuid,nodev,noexec`, and
  `/etc/sysctl.d/10-hardened-fs.conf` turns on the kernel's protections for
  shared directories.
- Linux `5.10.272-tag-` and the rest of Buildroot 2026.05.1 are unchanged from
  `0.4.0-raw.1`.

## Validation status

Two independent builds of the application and system packages are compared byte for byte and signed with the production key; the exact hashes are recorded in `HANDOFF-2026-11-09-RELEASE.md`.

Acceptance on the RC13 test devices is recorded in `HANDOFF-2026-11-09-RELEASE.md`: SSH state across the application update, the SSH-01 probe, account/key/data preservation, firewall and browser checks.

## Not tested in this release candidate

- Physical HDMI/video, OLED, WebRTC, Tailscale, power-cut and recovery-SD rollback.
- PicoClaw runtime/UI; the production image keeps terminal disabled.
- The real online update path from RC13 is exercised after publication.

## Recovery and limitations

- There is no automatic rollback for a raw update. Recovery is a reflash, and
  [`docs/sd-card-flashing.md`](../sd-card-flashing.md) describes it. A device
  where a partition write fails needs one.
- A device that is moved back to an application older than `2.1.4` gets the
  earlier key policy back with it.
- Moderate firewall mode filters by source address only, and Tailscale's own
  rules run ahead of the firewall modes. Both are described in
  [`docs/security-risk-inventory.md`](../security-risk-inventory.md).
- Not changed in this release: compiler hardening flags of the native video
  code, `debugfs` at boot, and the order of the vendor directories in `PATH`.
- The device cannot tell the browser about a changed certificate. After an
  update that changes it the page asks for a manual reload.
- This release does not claim that the SG2002 vendor delta is free of every
  upstream kernel CVE.
- Vendor firmware and runtime inputs still carry `NOASSERTION` license metadata.
- `serde_yaml` with `unsafe-libyaml` is an accepted, documented residual.
