# Hardened NanoKVM 2.1.7 RC16 + System 0.4.0 Raw 6

This release corrects two defects of RC15, and replaces it.

- **Video works again.** With RC15 the backend ended on the first frame of a
  video stream on every device that has an HDMI source, restarted, and logged
  the browser out. If you installed RC15 and the page keeps returning to the
  login screen, this is why.
- **Installing the application protects the SSH service accounts within
  seconds, without a reboot.** RC15 did that only after the next boot.

Everything else is RC15: the fix for the SSH authentication bypass that affects
every release before it, and what the second security audit of RC13 found.
Linux 5.10.272, the production signing key `hardened-system-prod-2026q3` and
RSA/SHA-256 signatures are unchanged. Applications `2.1.1` to `2.1.4` and
`2.1.6` were never published.

## Security: update if SSH is enabled

**CVE-2026-123158.** OpenSSH before 10.6p2, on a system that uses musl and no
PAM, accepts any password longer than 256 bytes for an account whose stored
password field is `*`, once another account has a password hash. Every
Hardened NanoKVM system before RC15 matches: its service accounts have that
field, root gets a hash at the first setup, and SSH is on by default.

- **Who can reach it:** any client that reaches port 22 of a device that was set
  up. No password or key is needed.
- **What it gives:** a login as a service account. Those accounts have no shell,
  so there is no command line and no file transfer. Port forwarding works, so
  the device can be used to reach the networks it is attached to, including the
  USB network of the computer it controls.
- **A shell as root** is reachable only on a device where someone changed the
  accounts by hand, for example root with a key and no password next to another
  account that has a password.

What fixes it:

- System `0.4.0-raw.6` carries OpenSSH 10.6p2, and every account of the image
  except root ships locked.
- Application `2.1.7` locks the service accounts of whatever system it runs on:
  at every start, and after an application update as soon as the update has
  finished, without a reboot. `sshd` refuses a locked account whatever password
  is offered.
- The `sshd` start script of the application also refuses those accounts by
  name and turns password login off for any account that has no password hash.
  A service that is already running takes these options at the next boot.

**What RC15 got wrong.** Its notes first said that application `2.1.5` locks
the accounts as soon as it is installed. It did not: the lock was requested
while the update still held the configuration writers, was refused and was not
repeated, so the accounts stayed open until the next boot. A device that took
both the application and the system update of RC15 is protected, because the
system update reboots it. A device that took only application `2.1.5` and has
not restarted since is not: reboot it, or install this release.

The project made one attempt at the upstream bypass, on a test device running
RC13, with a 300-byte password for the `daemon` account; it was rejected. The
bypass is therefore described from the upstream advisory and the source, not
reproduced on a device.

## Required install order

Keep a recovery SD card at hand and the power connected. A raw update rewrites
the boot and root partitions and takes about 15 minutes.

1. **Application first.** Install `2.1.7` before the system update: through
   **Settings → Update**, or through **Offline Update** with the archive,
   `latest.json` and `latest.json.sig` of this release. The system update
   refuses to install under an older application.
2. **System `0.4.0-raw.6` next.** In the **System Update** section press
   **Refresh**, enable **Allow raw system updates**, select **Download and
   Verify**, then install the staged update. The device reboots by itself and
   restores its settings on the first boot. Disable **Allow raw system updates**
   again afterwards.
3. **The full SD image** already contains both and needs neither step.

**Preview Updates** is not needed: the stable channels carry this release.

An installation older than application `2.0.42` first takes the `2.0.42` trust
bridge, as described in the
[key-transition notes](2.0.42-key-transition.md). A system older than
`0.3.0-raw.12` first takes `0.3.0-raw.12`.

## Changes since RC15

- **Video.** The image code took the size of an uncompressed frame from a table
  of bytes per pixel and, since RC15, rounded that entry down to a whole number.
  The capture format has 1.5 bytes per pixel, so a 1920x1080 frame was expected
  to be 2073600 bytes instead of 3110400, every captured frame was refused and
  the process ended with a fatal signal. The size is computed without rounding
  again, and a host test covers the capture sizes.
- **Application update and service accounts.** A new application that has just
  taken over waits for the update to release the configuration writers and then
  locks the service accounts. It asks twice a second for up to ten minutes and
  records the outcome in its log.
- **SSH after an application update without TLS.** A device that serves the web
  interface over plain HTTP now starts SSH again after an application update, as
  a device with HTTPS already did, when the switch had stopped a running
  service.
- **System `0.4.0-raw.6`** differs from `0.4.0-raw.4` only in the application it
  carries.

## Coming from RC13 or earlier

Everything that RC15 changed applies, and its notes describe it:
[what changes for you](rc15-2.1.5-raw.4.md#what-changes-for-you), the
[application](rc15-2.1.5-raw.4.md#application-215) and the
[system](rc15-2.1.5-raw.4.md#system-040-raw4). In short: only the release key is
trusted, accounts without a password log in by key only, nothing runs from
`/tmp` or `/dev/shm`, script uploads need a fresh terminal unlock, and a page
cached from an earlier version has to be reloaded before it can log in.

The list of trusted update keys still changes at the first boot under the new
application, not at the moment it is installed.

## Validation status

Two independent builds of the application match byte for byte (archive
`04a66be4…`, server `05d88562…`), and so do two independent builds of the
system (SD image `68c458bd…`, boot FIT `df4807a6…`, unchanged since RC13). The
application and raw system metadata are signed with
`hardened-system-prod-2026q3` and verify with its public key. On the build
commit the Rust suite passed 1377 and 110 tests, the host suite 77 with 9
device-only tests not run on the host, and Clippy shows no new warning.

Two test devices took the signed candidate through the offline application
update and the raw system update, from the previous unpublished candidate:

- **Service accounts.** After the application update alone, with no reboot,
  the log of each device shows the lock running 4.5 and 5.5 seconds after the
  new application took over. RC15 logged a refusal at the same point. Both
  devices already had locked accounts, so the change of an open account into a
  locked one is shown by the host test, not on a device.
- **SSH** kept running across the application update and came back by itself
  after the system update and after every reboot.
- **Video.** The device with an HDMI source delivered 1920x1080 MJPEG frames
  after the application update alone, after the system update and after a
  reboot, with no restart of the backend, and a browser showed the live
  picture. With RC15 the same check ended the backend every time. The other
  device has no source, so nothing about video was learned there.
- **After the update** both devices passed the checks for production-only
  trust, locked service accounts, account IDs, host key, OpenSSH 10.6p2, mount
  options and data mounts. The device without a source also passed the firewall
  mode round trip, the HDMI switch, the HID mode round trip with its two
  reboots, and the script upload, run and deletion.

## Not tested in this release candidate

- The update from the published RC15 or RC13 to this release before
  publication: both devices came from an unpublished candidate. The online path
  from RC15 is exercised on a third device after publication.
- H.264 and WebRTC streams: only the MJPEG stream was read.
- The **Download and Verify** page in a browser; the download and verification
  passed through the API in RC15 and the code is unchanged.
- A boot from a freshly written SD image.
- Physical HDMI hot-plug, OLED, Tailscale, power loss during an update and
  recovery from an SD card.
- PicoClaw runtime and its interface.

## Recovery and limitations

- There is no automatic rollback for a raw update. Recovery is a reflash, and
  [`docs/sd-card-flashing.md`](../sd-card-flashing.md) describes it. A device
  where a partition write fails needs one.
- A device that is moved back to an application older than `2.1.5` gets the
  earlier key policy back with it.
- Moderate firewall mode filters by source address only, and Tailscale's own
  rules run ahead of the firewall modes. Both are described in
  [`docs/security-risk-inventory.md`](../security-risk-inventory.md).
- Not changed in this release: compiler hardening flags of the native video
  code, `debugfs` at boot, and the order of the vendor directories in `PATH`.
- The device cannot tell the browser about a changed certificate. After an
  update that changes it the page asks for a manual reload.
- This release does not claim that the SG2002 vendor delta is free of every
  upstream kernel CVE.
- Vendor firmware and runtime inputs still carry `NOASSERTION` license metadata.
- `cargo audit` reports RUSTSEC-2026-0387 in `crypto-bigint` 0.5.5, reached
  through the WebRTC/DTLS dependency chain, and `pin-utils` and `unsafe-libyaml`
  as unmaintained. These are accepted, documented residuals.
